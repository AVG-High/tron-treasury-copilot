# USDD PSM 읽기 전용 상태

`src/chain/psm-status.ts`의 `getPsmStatus()`는 공식 TRON RPC에서 현재 USDD PSM 식별·양방향 토글·수수료를 요청 시 조회한다. 개인 지갑, 서명, 브로드캐스트, 승인, 자금 이동은 사용하지 않는다. 기존 배분 엔진의 `PsmState`와 분리하며, 조회 성공으로 USDD 추천·실행을 켜지 않는다.

## 조회와 해석

1. 기존 `verifyMainnet()`으로 고정 메인넷 genesis와 90초 이내 head를 확인한다.
2. 고정 PSM의 `usdd()`와 `gemJoin()`, 고정 Join의 `gem()`이 등록된 USDD·Join·USDT와 일치하는지 확인한다. 주소 반환값은 ABI 전체 32바이트와 상위 12바이트 0 패딩도 검사한다.
3. USDT `decimals()=6`, USDD `decimals()=18`을 확인한다.
4. `sellEnabled()`와 `buyEnabled()`는 정확한 0 또는 1만 허용한다. `sell`은 USDT→USDD, `buy`는 USDD→USDT다.
5. `tin()`과 `tout()`은 각각 진입·회수 수수료 비율의 WAD 원시값이다. `raw × 100 / 10^18`로 백분율 문자열을 계산한다. 예: `10^15 → 0.1%`, `10^18 → 100%`, 원시값 1은 `0.0000000000000001%`다. Number 반올림을 사용하지 않는다.

컨트랙트 읽기 9개는 순차 실행한다. 네트워크 확인 2개는 기존 RPC 검증기의 동시 읽기를 그대로 쓴다. 각 HTTP 요청의 타임아웃과 제한적 429/502/503/504 재시도는 공통 RPC 모듈에 따른다. 동일 블록 스냅샷이 아니며 `fetchedAt`은 전체 조회가 끝난 시각이다. 한 번의 관측을 향후 상태 보장으로 표시하지 않는다.

모든 조회가 성공해야 `quality=verified`다. 하나라도 실패하거나 형식·식별이 다르면 `quality=unavailable`, 토글·수수료 **모두 null**이다. 따라서 `false`는 성공적으로 확인한 비활성, `null`은 미확인이다. 중간 성공값을 최신 정상 상태처럼 내보내지 않으며 데모·과거 관측으로 대체하지 않는다.

`availableUSDT`는 항상 null이다. 토글만으로 Join/Vat 작동 상태, 부채·전역 한도, 실제 회수 가능액 또는 왕복 실행 가능성을 확인할 수 없기 때문이다. 조회 성공이 컨트랙트 감사·배포 바이트코드 재현 컴파일·실자금 왕복 검증을 뜻하지 않는다.

## 근거와 검증 범위

- [공식 배포 목록](https://docs.usdd.io/developers/deployment-addresses)과 [기존 주소 재검증](USDD-VERIFICATION.md)의 고정 주소를 사용한다.
- [공식 PSM 고정 커밋 소스](https://github.com/decentralized-usd/psm/blob/fce1b44a8ca12c9ff302eb374527d65ed04f165d/src/psm.sol)의 `sellGem`, `buyGem`, `tin`, `tout`, `WAD`를 2026-09-29 새로 읽어 방향·단위를 확인했다. 소스를 제품에 복사하지 않았다.
- `tests/psm-status.test.ts`는 가상 RPC로 주소·소수점 변조, 비정상 토글, 누락 반환, 마지막 읽기 실패, 잘못된 네트워크·오래된 head, 0/비영 수수료와 세밀한 단위를 검증한다. 테스트 성공은 실시간 RPC 성공이나 실제 교환 성공이 아니다.
- 새로운 네트워크 요청은 서버 읽기 전용이며 외부 주소를 입력받지 않는다. 화면과 API는 이 결과를 상태 설명에만 사용해야 한다.

## 이번 실제 읽기 결과

2026-09-29T17:27:59.525Z에 키 없는 공식 공개 RPC로 한 번 실행한 결과, 5.041초 후 HTTP 429 제한으로 `quality=unavailable`을 반환했다. 토글·양방향 수수료·가용 USDT는 전부 null이었다. 이전 조사에서 읽힌 1·0 값을 현재 상태로 재사용하지 않았다. 이 실행에는 단계 기록이 없었으므로 정확한 실패 호출은 확인하지 못했다. 이후 실패 단계 표시를 추가했다. 새 조회 모듈의 실시간 정상 응답은 이번에 검증하지 못했으며, 제출 시 공개 RPC 제한을 숨기거나 데모 수치를 실시간으로 표시하면 안 된다. 가상 RPC 검증과 전체 타입 검사를 수행했으며 실제 호출을 반복하지 않았다.

[TronGrid 공식 제한 문서](https://developers.tron.network/reference/rate-limits)는 키·계정·IP·엔드포인트·시간 단위별 제한을 설명하며, 키 없는 요청의 거절 가능성과 정책에 따른 QPS 변화를 명시한다. 따라서 근거 없는 고정 350ms 지연이나 새 RPC 주소를 해결책으로 추가하지 않았다. 앱의 순차 읽기·서버 조회 캐시를 유지하고 이 프로젝트 전용 서버 API 키 및 한도 확인을 안내한다. 공유 IP의 정확한 제한 원인이나 계정 쿼터는 이번 응답만으로 확정할 수 없다.
